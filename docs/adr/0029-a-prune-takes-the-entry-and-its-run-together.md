# A Prune takes the Entry and its Run together

> Amended by ADR 0030, ADR 0036.

`naiad queue list` had grown to nine lines of `done` before the first line of live work. Every Entry ever run stays in the listing, because an Entry is removed only when someone names its id, and nobody names an id for work that already ended. The Queue is the operator's one view of what is happening, and it was being read past rather than read.

We decided on `naiad queue prune`: it takes every Entry whose derived status is `done`, and the Run each became with it, as one act. The word matters as much as the behaviour — `clear` was the obvious name and is unavailable, because Clearing is discarding a Session's context (ADR 0019) and one word cannot carry both.

Only `done` is taken. `waiting` is future work, and cancelling it is what removing one by name is for. `running` backs a live Run the Supervisor is reading. `parked` is a Run asking for a human — idle-looking, unfinished, and the last thing a Prune should hide. Because the selection can reach nothing else, a Prune needs no confirmation prompt and no narrowing flag: there is nothing to be careful about, and `naiad queue list` already shows exactly which lines will go. Which Entries qualify is read through the same `status_of` the listing uses, so what the listing calls done and what a Prune removes cannot come apart.

The Run goes with the Entry, and this is the part a reader will not expect, because removing an Entry by name pointedly does not touch its Run. The two rules do not conflict; they rest on the same fact. `rm` leaves the Run alone because the Entry it removes may back a live session, and destroying that record would destroy something still in use. A Prune faces no such Run. What it leaves behind would be a Run directory nothing addresses any more — the Entry was the only thing naming it, and no command lists Runs directly. That is not an audit trail, because an audit trail you cannot reach is not one. So history lives exactly as long as its line in the listing, which gives a complete retention policy with no policy in it: the operator chooses the moment, and nothing expires behind their back.

Per Entry the file goes first and the Run second, and the order is the whole of the decision. `status_of` reads a Run whose directory has gone as `running`, deliberately — nothing in what remains says it ended (ADR 0013). So a Run deleted while its Entry survived would leave that Entry reading `running` for ever, invisible to every later Prune, and a listing that misreports done work as live is the one failure that costs more than the disk it saves. The reverse partial failure leaves an orphaned Run directory, reported by path, which is a thing the operator can act on. A refusal is recorded and the next Entry is taken anyway, because one stuck directory must not spare the whole backlog. The Queue is read whole before anything is deleted, so an Entry nobody can read stops the Prune with the file named rather than partway through work that cannot be taken back.

Two alternatives were rejected. Keeping the Run and deleting Entries only was the first instinct, and it grows an orphan set that only ever gets bigger, removable only by hand inside `~/.naiad` — which invites exactly the mistake the Naiad-owned home exists to prevent. Age-based collection was the second: it needs a policy, a trigger, and a clock, and it deletes records on a schedule nobody is watching, all to manage kilobytes of text.

## Consequences

A Prune is irreversible for the history it takes, so a done Run's Answer log and Run log must be read before its Entry is pruned rather than after. A finished Run's session is deliberately left alive, and pruning its Run is what finally severs the two: a Naiad command typed into that surviving session afterwards resolves to no Run and says so, where before it would have found one. That is the honest answer for work that has ended, and it is the visible cost of taking the record. Naiad gains its first destructive command, and it is deliberately the only one: nothing else removes a Run, and no age or size threshold exists to grow into a policy later. Withdrawing this decision means either restoring the orphan problem or inventing the retention rules this avoided.
