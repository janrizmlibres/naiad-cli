# A removed Entry cancels its Run

`naiad queue rm` took the Entry file out and pointedly left the Run alone, which made an Orphaned Run that had not ended. `naiad.runtime.resolve` — the single seam through which a Run is identified — keeps answering for such a Run, because it matches the pane and nothing says the Run is over. So the `SessionStart` hook injected the Protocol at every Clear, the `Stop` hook went on recording, and `state`, `ask`, `wait`, `hold` and `branch` all went on succeeding. Meanwhile the Supervisor, which derives its live Runs from the Entries on every pass, dropped this one at once. The agent was still being told to announce, into a Run nothing would ever tick again. It is the failure ADR 0035 removed, arriving through a second door: Naiad stopped, and nobody told the agent.

We decided that removing an Entry by name cancels the Run it became. Cancelling writes a line into that Run's log, which ends the Run — and a Run that has ended releases its Session (ADR 0035). Everything after that follows and needs no code of its own: the seam answers nothing, so the Protocol is injected into no fresh context there and the Protocol verbs refuse with the message that already exists, and `decide` returns Nothing. `RunLog.finished` becomes `RunLog.ended`, because a Run now ends two ways and all five of its callers were asking the one question already.

The cancellation is its own kind of line rather than the `finished` line a Finish writes. The Run log is the diagnostic a human reads, and a Run the operator called off must not read back six weeks later as one that completed. It names the State the Run was standing in, or no State at all when the Entry was removed before its agent announced anything.

A Run that was already over is not cancelled a second time. Its Session was released by the ending it has, so there is nothing to release, and a second line would say the operator called off work that had finished — which is the same lie the separate kind exists to prevent, written the other way round. It follows that the removal of a done Entry reports no cancellation either: what `rm` says about a Session is said only about a Session this act actually freed, or the operator is handed one that was never theirs to take.

The ending is written first and the Entry removed second, which inverts the order ADR 0029 turns on. The two orders are chosen against opposite failures. A Prune must not let a Run outlive its Entry, because a done Entry whose Run is gone reads as running for ever and the listing lies. Here an Entry must not outlive its release, because the window between the two writes is precisely the bug: a Run orphaned and still driving its Session. So a cancellation that cannot be written refuses the whole removal and leaves the Entry in the Queue, where the operator can see it and try again. A Run directory that is simply absent is not a failure — there is no Session to release, and the Entry naming it must not be trapped in the Queue by its absence.

There is no guard on a Run that reads as running. Prune refuses to delete such a Run because Prune selects by rule and reaches Runs nobody named, and Naiad never looks at tmux to tell a live Session from a dead one. Typing `naiad queue rm` names one Entry deliberately, so the operator has already made the judgment Prune cannot make for them. A confirmation prompt would also stop the command being usable from a script or from an agent inside a session.

Nothing is typed into the Session. The agent there learns at its next Protocol verb, from the refusal — which is when it acts, and which is the path ADR 0035 already chose. Typing into it instead would mean typing into a Session where the agent may be mid-turn, and `rm` has no tick loop to wait for a turn ending with. What `rm` does say, it says to the operator: it prints the Run it cancelled and the pane of the Session that is now theirs, so that a Session with an agent still working in it is not left silently behind.

We rejected three alternatives. The first is to derive the release from absence — teaching `resolve` to answer nothing for a Run no Entry names. It needs the seam to read the Queue, which it deliberately does not do, and absence is a third kind of witness beside the two ADR 0035 chose: nothing durable records it, and Prune would go on calling the orphan running and leaving it for the operator for ever. The second is to delete the Run with the Entry. Prune is the one deleter of Runs (ADR 0030), and the Run log is exactly what an operator wants when they are removing an Entry because something went wrong. The third is to reuse the `finished` line, which needs no reader to change at all and buys that by writing into the diagnostic a Finish that Naiad never carried out.

## Consequences

A cancelled Run reads done, so the next Prune takes it as a finished orphan. This is the reading ADR 0030 left open: an orphan made by `rm` used to read running for ever and be named at every Prune as the operator's to judge, and now it is judged at the moment of removal by the operator who typed the command. A running orphan can still arise — from a Prune whose Run removal failed, or from an Entry removed before this decision — and ADR 0030's caution is unchanged for those.

A cancelled Run's log lives only until the next Prune, since it has no line in the listing (ADR 0030). An operator who wants to read why a Run went wrong must read it before they prune.

This supersedes user story 20 of the Queue PRD — "removing an Entry leaves its Run and session alone, so that removal is a Queue operation rather than a destructive one". Removal is still not destructive: nothing is deleted, and the Run's whole record survives. What it no longer does is leave the Session claimed.

`naiad watch` over a cancelled Run reports that the Run has already ended, where it used to say "finished" for the one ending it knew. The word covers both endings, as `RunLog.ended` now does.

The `finished` field of `naiad.domain.decide.Signals` and `naiad.domain.supervise.Signals` keeps its name while carrying either ending. The pure core knows `Finish` as an Action and knows nothing of the Queue, and both fields mean the same thing to the rules — that nothing further is to be decided.
