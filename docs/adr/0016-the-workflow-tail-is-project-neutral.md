# The workflow tail is project-neutral; HCGPS is the one named skill

> Superseded in part by ADR 0018, and again by commit d856840 (the shipped tail ends when the pull request is open).

The shipped Workflow's `pull-request` State named `/hcgps-pr` outright, and the review tail below it waited for the "Claude Code Review check" by name and fixed against it. That is one repository's world written into the file — a GitHub host, the HCGPS monorepo's reviewers and base branch, a review integration only GitHub runs. Run the same Workflow against a repository elsewhere and the tail is wrong in three places at once: the skill it names, the review it waits for, and the review it fixes against.

We decided the tail opens a pull request generically. `pull-request` says "open a pull request"; the agent finds the GitHub MCP server that fits the repository in front of it and opens the request itself, comparing the branch against its base for the description. The one exception the prompt names is the HCGPS monorepo: its conventions — rebase onto `develop`, a build gate, named reviewers, excluded local-only files — are rich enough to earn a skill, so for it the prompt points at `/hcgps-pr`. Every other GitHub repository needs none of that and gets the bare open. The review wait, likewise, names no integration: it waits for whatever automated review the host runs, if any.

This is the same stance as ADR 0015 one layer up. Naiad refuses to know one repository's conventions because the Queue spans every repository on the machine, and the Workflow file is the other place that knowledge could hide. The bare "open a pull request" holds none of it. The single HCGPS pointer is less an exception to that than its proof: HCGPS's conventions live in the skill, and the file names the skill rather than inlining the reviewers, the base and the build — so even the one project it mentions is a reference and not a description.

The alternatives each put the variation in the wrong place. A Workflow file per project honours "swapping the file swaps the workflow" literally, but the tail is a dozen lines and the spine above it is three hundred of hand-tuned prose; copying all of it to vary the end is a standing invitation to drift, and the copies would. A per-Entry flag naming the skill has real precedent — the Working branch is a repo-convention fact the operator supplies per Entry — but it reopens the placeholder set `render_prompt` closes at five and argues in its own docstring against a sixth, and it buys explicitness at queue time for a fact the repository already knows about itself. Teaching Naiad to compose a shared spine with a per-project tail removes the duplication, but at the cost of a new engine capability and Naiad learning the shape of a Workflow it is built to stay ignorant of.

## Consequences

A plain GitHub repository works with no new skill: the agent opens its pull request through the GitHub MCP server, and the description comes from the branch diff. A skill is warranted only where a repository's conventions are rich enough to justify one, as HCGPS's are — and then the file points at it in a line rather than absorbing it. Onboarding a GitHub project is therefore nothing; onboarding one with special conventions is writing its skill and adding the pointer.

The third of the three faults — the review the tail fixes against — is not fixed by rewording, and `review-fix` keeps naming Claude Code Review on purpose. `/fix-review` reads that integration's own output format, so calling it generic would misdescribe what the skill consumes rather than free it from anything. What keeps the name a dependency stated where it lives, not a leak, is ADR 0017's branch: `review-fix` is reached only when a review has completed, so a host that runs none never arrives there. The wait above it, which every host meets, is where the neutral wording had to go; the fix below it, which only a Claude Code Review reaches, is where the name honestly stays.

GitHub is a precondition of this State. A repository not on GitHub — or with no GitHub MCP server configured — has nothing to open a pull request with. The Run routes nowhere special for it: the agent says why it cannot proceed and stops, and Naiad's ordinary path Nudges and then parks it, which is the honest record of a Run that needs a person. Rejecting non-GitHub work belongs at enqueue if it belongs anywhere, not in a branch of the tail built for a case that does not arise in practice.
