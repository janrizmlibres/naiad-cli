# The Clear is confirmed before the Prompt is delivered

Clearing was fire-and-forget: the loop typed `/clear`, slept a fixed settle time, and typed the Prompt, never checking that the Clear had landed. The Claude Code TUI can silently drop the typed `/clear` — observed once in ten real Clear-transitions of a shipped Run — and when it does, the next State's Prompt is delivered into the previous State's accumulated context, exactly the failure Clearing exists to prevent (ADR 0003). Naiad never noticed, because it never asked.

Widening the settle sleep is not the fix. The drop is not timing-caused: later Clears succeeded at tighter Stop→`/clear` gaps than the one that failed, so a longer wait has no evidence of preventing anything and only slows every Clear that was going to work. The honest move is to stop hoping and confirm — and Naiad already has a supported surface that fires on a Clear. The `SessionStart` hook runs on a fresh context and is told, in a documented field, whether the context is fresh from startup, from compaction, or from a Clear. So the Clear reports its own success the same way a turn's end already does, through a hook rather than by reading the TUI (ADR 0002 holds).

So delivery splits into two Actions where a State asks to be Cleared: a `Clear` that types `/clear` and waits, and a `Deliver` that sends the Prompt once the Clear is confirmed. The confirmation is a monotonic marker the `SessionStart` hook records only when its source is a Clear, read against a baseline the loop stamps when it issues the `Clear` — the same shape as a turn end, which is a monotonic `Turns.count()` read against the `Handled.turns()` baseline. A marker past the baseline means *this* State's Clear landed, not a Clear from some earlier State. If it does not appear within a confirm timeout the `Clear` is re-issued, and after a bounded number of attempts the human is told — a per-attempt timeout and an attempt cap, mirroring the silence-then-Nudge pair (`SILENCE_SECONDS`, `NUDGE_LIMIT`) that already governs a quiet agent. Delivering into an un-cleared context on exhaustion is never done deliberately: it is the bug.

The rule stays whole in the decision core (ADR 0004). It is the two-tick shape the Answerer already uses — `Consult` then `Respond`, with a record between them and `handled` written only by the terminal Action — so the loop gains no wait and no retry of its own; the waiting is elapsed time handed in as a signal, and the retrying is an Action returned. The intermediate `Clear` leaves the Announcement unhandled, so "act once per Announcement" is preserved in the sense that has always mattered: one Announcement is carried to one disposition, across as many ticks as that takes.

## Consequences

A Clear is no longer instantaneous from the loop's view — it spans ticks, and a State's Prompt is delayed until the marker confirms. On a Clear that lands the marker appears at once, so the delay is the confirm check, not the timeout; the timeout is only ever spent on a Clear that was dropped, which is the case worth spending it on. The fixed settle sleep in the tmux adapter's `clear()` therefore goes away: `clear()` types `/clear` and returns, and all waiting becomes the decision's, expressed as data.

This costs a new per-Run record for the Clear marker and a new baseline field beside the handled one — more of the bookkeeping ADR 0004 already keeps per Run, none of it module-global. And it makes Naiad depend on its own `SessionStart(clear)` hook being installed and able to write: if it is not, every Clear looks dropped and the Run stalls at the confirm-retry-notify path rather than silently delivering into stale context. That is the trade ADR 0002 already makes everywhere — a leak that is visible and recoverable is worth more than a dependency that fails silently at the worst moment.
