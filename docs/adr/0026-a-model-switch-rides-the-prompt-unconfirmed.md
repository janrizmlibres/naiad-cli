# A model switch rides the Prompt, unconfirmed

> Amended by ADR 0038, ADR 0039, ADR 0040, ADR 0059.

A Workflow's phases do not all want the same model: a design grill earns the expensive one, a mechanical review-fix does not, and on an unattended overnight Run nobody is at the keyboard to switch. So a State may declare `model` and `effort` in the Workflow file, beside `prompt` and `clear`, because which model a phase needs is a judgment about the phase's nature — the same judgment that chose its Prompt — and not a property of the individual task. There is deliberately no Entry-level override: a real "this whole task needs the big model" case can earn one later, and adding it now would buy a precedence rule before any need for it exists.

Both values are opaque strings, like a Subject or a Predecessor (ADR 0015). Naiad validates them against nothing: Claude Code is the authority on what names a model, and any list Naiad kept would rot — a stale allowlist refusing a valid new model blocks correct Workflows indefinitely, where a typo is caught the first time the file is run and fixed once. `model = "default"` is legal to write for exactly this reason; whether it is legal to *mean* is the session's report to make.

Absence is the sharp edge, because a model set in the session is sticky. If the author annotates only `grill`, every later State silently inherits it — an order-dependent surprise that shows up as wrong cost or quality with nobody watching. So absence is made unrepresentable rather than interpreted: a file where any State declares `model` must carry a file-level `model` default (and likewise `effort`), refused at parse otherwise, the same top-level-defaults-with-override shape a Batch file already uses. Every State then has an effective value readable off the file with no mental replay of the Run's path — or the file mentions neither key anywhere, and Naiad never touches the session's settings at all.

The switches ride Prompt delivery. Into a running session that means typing `/model` and `/effort` before the Prompt — after a confirmed Clear, since delivery is what they are part of; at kickoff, where the first Prompt is handed to the session as it starts, they ride the same way as launch flags. Typed on *every* delivery, not only on change: it is two keystroke lines, and it self-heals a switch that was previously dropped. Riding delivery also settles the Gate State without a special case — no Prompt, nothing typed, "Naiad delivers nothing and takes no action" stays literally true, and the human present can set their own.

And the switch is best-effort where the Clear is confirmed (ADR 0019). This is not the same failure: a Prompt delivered into an un-cleared context poisons the work — the one thing Clearing exists to prevent — while a Prompt run on the wrong model produces correct work at the wrong price or quality. Claude Code fires no hook on a model switch, and reading the session's state back to verify is what ADR 0002 forbids; degradation does not justify inventing a confirmation channel the platform does not offer, where corruption did. The every-delivery retyping is the mitigation: a dropped switch mis-runs one State, not the rest of the Run.

The Answerer is covered by the same file, differently shaped: an optional `[answerer]` table with its own `model` and `effort`, passed as `--model`/`--effort` flags on the headless invocation. Both keys optional and absence meaning no flags, with no required-default rule — a headless session starts clean every time, so there is no stickiness to guard against and absence is genuinely unambiguous. One Answerer model per Run falls out of the session being resumed across its Questions.

## Consequences

A State's effective model becomes legible in the Workflow file and nowhere else — Naiad records what it typed in the Run log like any other delivery, but never knows whether it took. The failure mode this accepts is a Run that quietly runs a State on the wrong model when a typed switch is dropped and its own delivery's retype also fails; the failure it refuses is a stalled Run or an invented confirmation surface. Workflow files gain two keys and one refusal rule, and the refusal means a file that validated yesterday keeps validating — the rule only ever fires on files that use the new keys ambiguously.
